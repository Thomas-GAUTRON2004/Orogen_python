## Reproducible benchmark harness

The current harness compares the vendored upstream JavaScript reference with
three execution modes: JavaScript, Python with all Orogen Numba dispatch paths
disabled, and Python with Numba enabled. It measures deterministic inputs on
one GitHub Actions runner.

Run locally after installing the optional speed extra:

```bash
python -m pip install -e ".[speed]"
BENCH_ROUNDS=10 BENCH_WARMUPS=2 node benchmarks/bench.mjs > benchmark-results.json
python benchmarks/render_report.py benchmark-results.json
```

The default protocol performs **10 measured repetitions after 2 warmups**.
Each metric stores median, mean, sample standard deviation, 95th percentile,
minimum, maximum and raw samples. Results are emitted as JSON, Markdown and
CSV. CI publishes all three as a 90-day Actions artifact and adds the Markdown
report to the workflow summary.

Common paired workloads are FBM, batched spherical geometry, graph BFS,
connected components, Dijkstra, crust creation/snapshot and crust batch copy.
Python pure and Python + Numba are timed for every workload. Far-field
diffusion is additionally compared within Python with and without Numba.

### Adding a function to the comparison catalog

The paired harness is designed to grow as more JavaScript functions are ported.
The workload catalog is the single source of truth for report labels and which
comparison mode a workload belongs to:

- `benchmarks/catalog.json`: stable workload IDs, display labels and grouping.
- `benchmarks/bench.mjs`: JavaScript implementation and timing for paired workloads.
- `benchmarks/bench_python.py`: Python fallback and optional Numba timings.
- `benchmarks/render_report.py`: reads the catalog to generate Markdown/CSV
  tables and checks that every catalog entry was emitted by the expected runners.

#### Registering a paired JavaScript/Python function

1. Add a deterministic fixture/setup function to the relevant runner. Build
   fixtures outside the timed callable unless setup cost is intentionally part
   of the benchmark.
2. Add the JavaScript measurement to the object returned by
   `benchmarkJavaScript()` in `benchmarks/bench.mjs`.
3. Add the matching Python measurement under the same stable ID in the
   `timings` dictionary in `run_mode()` in `benchmarks/bench_python.py`.
   The function is measured in both pure-Python and Numba modes automatically.
4. Add one entry to the `paired` array in `benchmarks/catalog.json`:
   `{"id": "my_function_ms", "label": "My function (fixture description)" }`.
   The ID must match the key emitted by both runners.
5. Run the local command below. Report generation fails with a clear catalog /
   runner mismatch if either side forgot to emit the registered ID.

#### Registering a Python-only port target

Add the benchmark to the Python-only results returned by `run_mode()` (outside
the common `timings` mapping), then add its stable ID and label to the
`python_only` array in the catalog. This gives an immediate pure-Python versus
Numba comparison while the JavaScript equivalent is still being ported. When a
JavaScript reference becomes available, move the workload into `paired` and
emit the matching JavaScript timing.

#### Measurement rules

- Keep stable IDs independent of implementation names so a port can evolve
  without rewriting historical report consumers.
- Use the same deterministic input, logical work and output/sink in both
  implementations. Document unavoidable differences in fixture granularity.
- Keep fixture construction and JIT compilation out of timed samples unless
  they are explicitly the target.
- Preserve raw samples and summary statistics; do not add hard performance
  pass/fail thresholds based on shared-runner timings.
- Add correctness/differential tests separately. A faster result is not evidence
  of semantic equivalence.

The initial-world builder A/B is a separate production-constructor benchmark,
not a paired JavaScript function yet. Its baseline is the PR target branch.
The same report artifacts and summary mechanism are used for all benchmark
outputs.

### Tectonic step benchmark

The harness also measures one real `step_world` call on a deterministic,
prebuilt spherical mesh with four plates. It times independent worlds per
repetition so every sample begins from the same initial state. Mesh generation
and world construction are outside the timed region; the timing includes the
actual step orchestration and its configured resolve/classification/tectonic
stages.

There is deliberately no JavaScript timing for `step_world`: the Python port
does not yet have a complete equivalent JavaScript tectonic orchestrator in
the vendored reference set. This is a Python pure-versus-Numba comparison,
not a claim of whole-engine JavaScript parity.

### Interpretation notes

- A Python/JavaScript ratio below 1 means Python is faster; a Numba gain above
  1 means the accelerated Python path is faster than the Python fallback.
- BFS, connected components and Dijkstra use a synthetic degree-6 CSR ring,
  not a production planet mesh. Dijkstra uses a 20,000 km cutoff.
- Geometry and FBM use batched Python APIs while the upstream JavaScript
  reference exercises scalar calls. Crust batch APIs also differ in call
  granularity from the scalar JavaScript reference. These figures compare
  actual implementation paths, not a language-only abstraction.
- Shared hosted runners vary. Compare medians and dispersion across repeated
  runs; do not interpret a single sample as a universal speed guarantee.
- Python process launch, mesh construction and step-world preparation are
  excluded from timed regions. Numba warmup/JIT compilation is also excluded.

## What changed

- FBM moved from about **48× slower** to near parity or slightly faster than the JS reference on the measured batch workloads.
- BFS moved from about **28.6× slower** to around **1.4–1.9× slower** across the latest runs.
- The full callback-free mesh Dijkstra traversal is now compiled; the latest synthetic benchmark measured about **49× faster** than the JS sample, but that result must not be extrapolated to full-world graphs.
- The real tectonic far-field `spread_push` traversal is also compiled as one batch; its full-path A/B benchmark measured **3.35× faster** than the Python fallback.
- Geometry and crust snapshots remain major performance gaps. Shared-runner results vary and remain directional.

## Numerical-equivalence policy

- Numba kernels use float64 inputs and outputs for noise, preserve the same operation order, and set `fastmath=False`.
- The Numba FBM results are checked bit-for-bit against the retained pure-Python implementation.
- BFS uses the same CSR adjacency, ascending source initialization, FIFO traversal, and int16 distance output. Its compiled path is used only when `can_enter` is absent; arbitrary Python predicates retain the original Python implementation.
- Dijkstra retains the JS heap push/pop ordering, ascending seed insertion, lazy stale-entry checks, max-distance cutoff, and writes the value stored in the destination array back to the heap (including float32 rounding). Its Numba path is used only without `can_enter` or `on_reach`; callback-based calls use Python. Differential tests compare float32 and float64 arrays.
- Far-field diffusion compiles weighted graph traversal, great-circle edge costs, source propagation and reached order; crust history fields are then updated in Python. Its output is checked against the Python fallback.
- The pure-Python path remains available when Numba is not installed.
- Differential checks against the upstream JavaScript implementation remain part of CI. Performance is accepted only alongside numerical and behavioural tests.

## Method and limitations

- Timings are medians of five measured runs after one warm-up; they are microbenchmarks, not end-to-end planet-generation timings.
- The mesh benchmark uses a synthetic 12,000-cell degree-6 ring graph, not a production spherical mesh. The Dijkstra workload also stops at `max_km=20,000`, so it does not visit every cell.
- The benchmark does not measure Delaunay/sphere-mesh generation, full tectonic `step_world`, long geological histories, memory use, or complete planet generation. The far-field A/B uses a synthetic equatorial ring graph and has no direct JavaScript comparison.
- Python FBM uses one batch call to amortize Python-to-Numba call overhead. Scalar `noise3d` and `fbm` methods are also JIT-dispatched, but real pipeline speed depends on call patterns.
- Results depend on the hosted runner and are a baseline, not a universal JavaScript/Python ratio.

## Crust raster batch storage, snapshots and copy kernels — 2026-11-17

The raster now allocates one backing matrix per NumPy dtype and exposes each named field as its own contiguous, writable one-dimensional view. This reduces allocation count without changing the field names, individual dtypes, cell indexing or CELL_FIELDS order.

The batch APIs are now used in real tectonic paths:

- resolve gap growth groups new ocean-crust cells by plate and initializes each group with create_many; fracture, trench and occupancy updates retain their original per-birth order.
- rift splitting moves the known set of cells with copy_many and remove_many.
- plate welding groups upper/lower crust remapping and hole filling through copy_many, while keeping the selection/filter stages that depend on previously written cells in their original order.
- copy_many uses a cache-friendlier field-major traversal for distinct source/destination rasters. Same-raster copies retain sequential cell order so overlapping reads observe earlier writes just like repeated scalar copy_from calls. Repeated destination cells with a frame rotation rotate the final copied far-field axis only once.
